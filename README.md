Опис усіх тест-кейсів (кроки, очікувані результати, матриця покриття) — у [`test-cases/`](test-cases/README.md).

## Запуск

Перший запуск:

```bash
npm ci
npx playwright install chromium
```

| Команда | Що робить |
|---|---|
| `npm test` | Регресія: усі тести (UI + API), крім тестів на відомі баги. Має бути зеленою |
| `npx playwright test --headed --workers=1` | Усі тести в одному видимому вікні, по черзі |
| `npm run test:ui` | Тільки UI, без відомих багів |
| `npm run test:api` | Тільки API, без відомих багів |
| `npm run test:headed` | Тільки UI, одне видиме вікно, по черзі |
| `npm run test:watch` | Playwright UI mode: список тестів, запуск по кліку, покроковий перегляд |
| `npx playwright test --grep @negative` | Тільки негативні тести |
| `npm run test:known-bugs` | Тільки тести на відомі баги (тег `@known-bug`), окремий звіт |
| `npm run test:all` | Усі тести разом, включно з відомими багами |
| `npm run report` | Відкрити HTML-звіт регресії |
| `npm run report:known-bugs` | Відкрити HTML-звіт прогону відомих багів |
| `npm run bugs:publish` | Прогін відомих багів + оновити `BUGS.md` |

Очікуваний результат: `npm test` — **17 passed, 0 failed**, код виходу 0. `npm run test:known-bugs` — **11 failed**: це 11 відкритих багів продукту, кожен підтверджено сигнатурою (див. [Знайдені баги](#знайдені-баги)).

Локально браузер **видно** за замовчуванням, у CI тести йдуть headless.
Змінні оточення: `HEADLESS=1` ховає вікно. **Ручний запуск уповільнено**: коли браузер видно (локально, зокрема зелена стрілка в IDE), кожна дія виконується із затримкою 300 мс, щоб за тестом можна було стежити. `SLOWMO=800` уповільнює сильніше, `SLOWMO=0` вимикає затримку. У CI, з `HEADLESS=1`, у `bugs:publish` і в генераторі тестів затримки немає.

**Оточення API.** Restful Booker — спільна публічна пісочниця: дані на ній періодично скидаються, а інші користувачі створюють і видаляють свої бронювання. Тому тести не покладаються на чужі id: кожен тест створює своє бронювання з унікальним прізвищем через фікстуру `bookings`, яка видаляє його після тесту, навіть якщо тест упав. Те саме стосується бронювань, які API помилково приймає в тестах валідації. Для неіснуючого бронювання використовується id `2147000000`, який не збігається з реальними.

## Як написано тести

Спеки імпортують усе з одного місця — `'@ui'` або `'@api'` (аліаси в `tsconfig.json` на `src/ui.ts` / `src/api.ts`). Ядро бере на себе шаблонну роботу, щоб у тесті лишались кроки й перевірки:

| Хелпер | Що робить |
|---|---|
| `meta('Major', '<передумова>')` | Серйозність і передумова для баг-репорту — один рядок замість блоку `annotation` |
| `meta('Major', { knownBug: 'Received: 500' })` | Тест виявляє **відомий баг**: отримує тег `@known-bug` і виходить з регресії в окремий прогін; `knownBug` — сигнатура бага в помилці (див. [Знайдені баги](#знайдені-баги)) |
| фікстура `loggedIn` | Сесія `standard_user` через cookie, одразу відкритий каталог. Форму логіну перевіряє тільки `login.spec.ts`, тож її поломка не валить решту UI-тестів |
| `PATHS.cart`, `PATHS.checkoutInfo`, … | Сторінки SauceDemo як шаблони URL: `expect(page).toHaveURL(PATHS.cart)` |
| `expect(amount).toEqualMoney(37.98)` | Порівняння грошей у центах; у помилці — `Expected: $37.98, Received: $37.97` |
| `await expect(response).toHaveStatus(400)` | Статус API; у помилці — ще й URL і тіло відповіді |
| `expectQuick(...)` | Короткий таймаут для перевірок «застосунок НЕ має перейти» |
| фікстура `bookings` | `bookings.create()` / `createRaw()` — бронювання видаляються після тесту, навіть якщо він упав |
| `addToCart(PRODUCTS.backpack, PRODUCTS.onesie)`, `cartButton(product)` | Page Objects приймають сам товар і кілька товарів одразу |

Кроки (`test.step`) лишаються в спеках свідомо: з них репортер будує розділ «Кроки» баг-репорту, і вони мають описувати дії користувача, а не назви методів.

## CI
GitHub Actions (`.github/workflows/playwright.yml`) запускається на кожен push і PR.
Job має два кроки з тестами:
- **Regression (must be green)** — `npm test`, усе крім `@known-bug`. Визначає статус CI: у звіті цього кроку нуль червоних тестів, тож будь-який червоний — нова проблема.
- **Known bugs (informational)** — `npm run test:known-bugs`, з `continue-on-error: true`. Тести на відомі баги червоні й на статус CI не впливають.

Артефакти run'у: `playwright-report` (HTML-звіт регресії), `playwright-report-known-bugs` (HTML-звіт відомих багів), `bug-reports` (`BUGS.md` — падіння регресії, `KNOWN-BUGS.md` — відомі баги), `test-results` з trace і скриншотами упалих тестів обох прогонів. Обидва баг-репорти також виводяться в **Summary** job'а.

## Свідомо не покрито

Межі задає завдання: основні сценарії для `standard_user`, CRUD-флоу бронювання і 2–3 негативні кейси на кожну систему. Усе, що виходить за ці межі, не покрито свідомо:

| Що | Чому не покрито |
|---|---|
| Інші користувачі SauceDemo: `problem_user`, `performance_glitch_user`, `error_user`, `visual_user` | Завдання обмежене `standard_user`. Ці користувачі навмисно зламані розробниками SauceDemo: тести на них перевіряли б відомі демо-дефекти, а не сценарії |
| Firefox, WebKit, мобільні розміри екрана | Крос-браузерність не входить у завдання, а прогін утричі довший. Додається одним project'ом у `playwright.config.ts` |
| Решта бургер-меню (All Items, About), футер і посилання на соцмережі | Не входять в основні сценарії із завдання. Із меню покрито Reset App State (на ньому знайдено баг) і Logout (згенеровано [конвеєром](#бонус-тест-кейс-текстом--playwright-тест)) |
| **Dynamic Catalog** у бургер-меню: підменю Lazy Load, Spinner, Slider (`/dynamic-catalog-lazy-load.html`, `/dynamic-catalog-spinner.html`, `/dynamic-catalog-slider.html`) | Розділ з'явився на сайті вже після того, як тести були написані; помічено на скриншоті падіння 2026-11-25. Це три сторінки каталогу з динамічним завантаженням, і розмітка в них інша, ніж в основному каталозі (звичних карток `inventory-item` немає). В основні сценарії завдання вони не входять. Кандидат на наступні тести: очікування динамічного контенту без `waitForTimeout` |
| Сортування A→Z | Покрито три з чотирьох варіантів: ціна ↑, ціна ↓ (згенеровано конвеєром) і назва Z→A. A→Z — порядок за замовчуванням, та сама логіка у зворотному порядку |
| Межові значення полів чекауту (довжина, Unicode, формат індексу) | Вимог до формату немає, тому очікувану поведінку визначити неможливо (див. [Питання до вимог](#питання-до-вимог)). Покрито порожнє поле і поля з самих пробілів |
| Візуальні регресії, доступність (a11y), продуктивність, навантаження | Інші види тестування, не функціональні сценарії із завдання. Навантажувати спільну публічну пісочницю ще й некоректно |
| API: `GET /booking` з фільтрами, Basic auth, `GET /ping` | Не входять у флоу «авторизація → створити → змінити → видалити → перевірити». `PATCH` покрито тестом, згенерованим конвеєром |
| Перевірка JSON-схеми відповідей | Тести порівнюють тіло відповіді з надісланими даними повністю (`toEqual`), і для цього обсягу це сильніша перевірка, ніж схема. Схема знадобиться, коли тестів на читання стане більше |
| Безпека поза доступом: XSS, SQL-ін'єкції, brute force, підробка токена | Окремий вид тестування. Покрито тільки базовий контроль доступу: невірний пароль, заблокований користувач, зміна без токена, сторінки чекауту без логіну |
| Ізоляція даних між паралельними користувачами пісочниці | Пісочниця спільна, і її стан тести не контролюють. Тому кожен тест працює лише зі своїми бронюваннями й прибирає їх (див. [Оточення API](#запуск)) |

## Знайдені баги

Баги не описуються вручну: **баг-репорт генерується з упалого автотесту**.
Тести, що знаходять баги, лежать у загальних спеках поруч з іншими тестами своєї області і перевіряють **правильну** поведінку. Поки баг існує, тест червоний.

**Відомі баги — окремий прогін.** Тест на відомий баг перевіряє правильну поведінку й має сигнатуру бага в `meta()`. Сигнатура — це те, як баг проявляється в помилці:

```ts
test('POST /booking without required fields returns 400', meta('Major', { knownBug: 'Received: 500' }), async …
```

`meta()` з `knownBug` додає тесту тег `@known-bug`. Прогін розділено за цим тегом стандартними `--grep` / `--grep-invert`:

| Прогін | Команда | Що входить | Статус |
|---|---|---|---|
| Регресія | `npm test` | усе, крім `@known-bug` (17 тестів) | **має бути зеленим**: будь-який червоний тест — нова проблема |
| Відомі баги | `npm run test:known-bugs` | тільки `@known-bug` (11 тестів) | інформаційний: тести червоні, поки баг існує; у CI крок з `continue-on-error` |

Статус прогону визначає сам Playwright, репортер його не змінює. У звіті прогону відомих багів репортер позначає кожне падіння:

| Позначка | Коли |
|---|---|
| Відомий баг, підтверджено | Тест упав, і **кожна** помилка містить сигнатуру |
| 🆕 Баг проявився інакше | Тест упав, але помилка інша: інший статус чи текст. Треба перевірити |
| Потребує тріажу | Мережа, 502/503/504, таймаут, неоднозначний локатор, помилка в коді тесту |
| ✅ Можливо виправлено | Тест **пройшов**: перевір і, якщо баг виправлено, прибери `knownBug`, і тест повернеться в регресію |

Сигнатура тут — підказка для людини, а не гейт: вона впливає лише на позначку в звіті.

**Як це працює** (репортер `src/reporters/bug-report.ts`):
- **Кроки** беруться з `test.step(...)`; крок, на якому тест упав, позначено ❌.
- **Очікуваний результат** — це повідомлення assertion (`expect(x, '<очікувана поведінка>')`) плюс рядок `Expected`.
- **Фактичний результат** — рядок `Received` з помилки.
- **Серйозність і передумова** — анотації тесту `severity` і `precondition`.
- Також у репорт потрапляють оточення, шлях до тесту, повна помилка, скриншот і trace.
- Тест, що впав, але пройшов на retry, вважається нестабільним (flaky) і багом **не** вважається.

**Обмеження: падіння ≠ баг.** Тест падає з будь-якої причини, а не тільки через баг продукту: пісочниця відповіла 503, мережа обірвалась, змінився локатор. Тому кожен репорт — це **кандидат** у баги, який людина підтверджує перед тим, як заводити його в трекер. Частину таких випадків репортер відсіює сам: падіння з ознаками проблеми оточення чи тесту (мережеві помилки, 502/503/504, таймаут тесту, неоднозначний локатор, `TypeError` у коді тесту, закритий браузер) потрапляють у розділ **«Потребує тріажу»**, а не в список багів. Відсіяти все неможливо: якщо на сайті перейменують `data-test`, падіння «елемент не знайдено» виглядатиме так само, як баг. Тому для UI до репорту прикладаються скриншот і trace.

**Де дивитися:**
- [`BUGS.md`](BUGS.md) — опублікована копія з останнього прогону відомих багів (`npm run bugs:publish`).
- У CI — артефакт `bug-reports` і **Summary** job'а: репорти генеруються на кожному push.

> Тести на відомі баги червоні у своєму окремому звіті: це відкриті баги. У звіті регресії їх немає. Щойно баг виправлять, тест стане зеленим і з'явиться в розділі «Можливо виправлено». Це нагадування закрити баг і прибрати `knownBug`, щоб тест повернувся в регресію.

### Задокументовано, але розходиться з HTTP-семантикою
Це не баги: поведінка описана в [документації API](https://restful-booker.herokuapp.com/apidoc), і тести перевіряють саме її.
- Успішний `DELETE /booking/{id}` повертає **201 Created**, хоча за семантикою HTTP очікувався б 200 OK або 204 No Content. CRUD-флоу перевіряє задокументований 201.

### Перевірено, не баг
- Податок на чекауті — 8% від Item total, Total = Item total + Tax (для $29.99: Tax $2.40, Total $32.39).
- `POST /booking` з битим JSON → 400 Bad Request.
- `PUT /booking/{id}` з невалідним токеном → 403 Forbidden.
- `GET /booking/abc` → 404 Not Found.
- Для незалогіненого користувача сторінки чекауту за прямим URL закриті: «You can only access '…' when you are logged in».

### Питання до вимог
Знайдено вручну, але не віднесено до багів, бо очікувана поведінка не визначена вимогами:
- **Формат Postal Code.** Поле приймає будь-які символи (наприклад, `abc!@#`). Чи потрібна валідація, залежить від того, для яких країн працює магазин.
- **Збереження сортування.** Після повернення зі сторінки товару (**Back to products**) сортування скидається на Name (A to Z). Невідомо, чи має воно зберігатися.

## Бонус: тест-кейс текстом → Playwright-тест

| Команда | Що робить |
|---|---|
| `npm run generate -- generator/cases/01-logout.md` | Один кейс |
| `npm run generate -- --all` | Увесь пул `generator/cases/` |
| `npm run generate -- "generator/cases/0*.md" --dry-run` | Кейси за шаблоном; тільки план, без викликів моделі |

У пакетному режимі наявні спеки пропускаються (`--force` — перегенерувати), у пул потрапляють тільки спеки, що пройшли, а зведення пишеться в `generator/runs/batch-summary.md`.

`scripts/generate-test.mjs` бере текстовий тест-кейс (передумова, кроки, очікуваний результат) і збирає промпт з правил `.claude/CLAUDE.md`, Page Objects, фікстур і прикладу спеки. Далі він викликає **Claude Code в headless-режимі** (`claude -p`, без інструментів), записує спеку в `tests/<ui|api>/generated/`, запускає typecheck і тест. Якщо тест упав, конвеєр передає помилку моделі на виправлення (`--fix N`). Наприкінці він ставить вердикт: `passed`, `possible product bug` (тест падає на assertion) або `failed` (проблема в коді).

| # | Вхід | Чи пройшло | Що правили руками |
|---|---|---|---|
| 1 | Вихід із системи | ✅ з 1-ї спроби | Модель не вигадала відсутній метод логауту, а позначила 3 × `TODO(page-object)`; ми винесли локатори в `HeaderComponent` і текст помилки в `ERRORS` |
| 2 | Сортування за ціною від дорожчих | ✅ з 1-ї спроби | Нічого |
| 3 | `PATCH /booking/{id}` | ✅ з 1-ї спроби | Нічого |
| 4 | Чекаут з порожнім кошиком (відомий баг) | ❌, вердикт `possible product bug` | Після падіння модель **не послабила** assertion під баг. Спеку прибрали з пулу, бо вона дублює `UI-CHK-04` |

### Де агент помилився і як це помітили

Кожну помилку після виправлення записано як правило в скіл агента, щоб він не повторив її в наступних задачах.

| # | Помилка агента | Як помітили | Що виправили | Де зафіксовано |
|---|---|---|---|---|
| 1 | Окремий `testDir` для кожного project'у: UI-тести не запускались зеленою стрілкою в IntelliJ, бо IDE брала `testDir` останнього project'у (`api`) | **Я** — стрілка в UI-спеці перекидала на `name: 'api'` у конфігу | Спільний `testDir` + `testMatch` для кожного project'у | скіл `debug-failing-test`, коментар у `playwright.config.ts` |
| 2 | Хибна гіпотеза про причину (лапки в назвах тестів), «підтверджена» некоректною перевіркою | **Агент** — та сама перевірка впала і на назвах без лапок | Знайшли справжню причину (п. 1) | скіл `debug-failing-test`: перевіряти гіпотезу контрольним випадком |
| 3 | Тести на баги винесені в окрему спеку з `test.fail()`, а баг-репорти написані вручну | **Я** — баги мають бути в загальному пулі тестів, а репорти — з падінь | Тести в загальних спеках, баг-репорти генерує репортер `src/reporters/bug-report.ts` | скіли `add-ui-test`, `add-api-test`, `debug-failing-test`; `CLAUDE.md` |
| 4 | Задокументована поведінка (`DELETE` → 201) записана як баг, хоча позитивний тест перевіряв саме 201; вигадана вимога до формату Postal Code | **Рецензент** — помітив протиріччя між списком багів і тестом | `DELETE` → 201 перенесено в «Задокументовано, але розходиться з HTTP-семантикою», Postal Code — у «Питання до вимог» | скіли `add-api-test`, `add-ui-test`; `CLAUDE.md` |
| 5 | «Падіння = баг»: будь-яке падіння (503 пісочниці, зламаний локатор) ставало б баг-репортом | **Рецензент** — `test.fail()` проходить при будь-якому падінні; та сама проблема лишалась і в репортері | Тріаж у репортері: мережа, 502/503/504, таймаут, strict mode, `TypeError` → «Потребує тріажу»; обмеження описано в README | скіл `debug-failing-test`; `CLAUDE.md` |
| 6 | Негативні кейси логіну отримали пріоритет P2, хоча це перевірки доступу | **Я** — «дивний пріоритет для негативних тестів логіну» | Підвищено до P1, шкалу уточнено: P1 = критичний шлях **або безпека** | скіл `add-ui-test` |
| 7 | Assertion задом наперед: `expect([200, 204]).toContain(status)` — у баг-репорті «фактично: [200, 204]» | **Агент** — побачив безглузде значення в згенерованій таблиці багів | `expect(String(status)).toMatch(/^(200\|204)$/)` | скіл `add-api-test` |

Дрібніші помилки, які агент помітив і виправив сам: неточний локатор кнопки в картці товару (strict mode); `--list` перезаписував звіт репортера порожнім; `awk` з Windows-шляхом мовчки видалив розділ README; `;` у npm-скрипті не працює в `cmd`; `cross-env`, якого немає в залежностях. Усі вони теж записані в скіли (розділи «Типові помилки агента»).
