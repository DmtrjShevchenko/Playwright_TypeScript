# Бонус: конвеєр «тест-кейс текстом → Playwright-тест»

| Команда | Що робить |
|---|---|
| `npm run generate -- generator/cases/05-111.md` | Один кейс |
| `npm run generate -- --all` | Усі кейси з `generator/cases/` |
| `npm run generate -- generator/cases` | Те саме: папка |
| `npm run generate -- "generator/cases/0*.md"` | Кейси за шаблоном (його розгортає сам скрипт, тому працює і в PowerShell, і в cmd) |
| `npm run generate -- generator/cases/06-*.md generator/cases/07-*.md` | Кілька файлів |
| `npm run generate -- --all --dry-run` | Що буде згенеровано, без викликів моделі |
| `npm run generate -- --all --force` | Перегенерувати й ті кейси, для яких спека вже є |

| Прапорець | Що робить |
|---|---|
| `--all` | Пул за замовчуванням — `generator/cases/` |
| `--force` | Без нього кейс, для якого спека вже є, **пропускається**: ручні правки після рев'ю не затираються. З `--force` спека перегенеровується; якщо нова версія не пройде, повертається попередня |
| `--dry-run` | Показує, які кейси буде згенеровано або пропущено, нічого не викликаючи |
| `--fix N` | Скільки разів після падіння передати помилку моделі на виправлення (за замовчуванням 1) |
| `--model` | Модель для `claude -p` |

- **У пул потрапляє тільки спека, що пройшла.** Якщо тест упав, навіть з вердиктом `possible product bug`, спека лишається тільки в `generator/runs/<кейс>/` для рев'ю, а в `tests/` її немає. Так пакетний прогін не додає в CI неперевірених червоних тестів.
- **Зведений звіт пакетного прогону** зберігається в [`runs/batch-summary.md`](runs/batch-summary.md): статус, спроби, час, вартість, чи потрапив тест у пул, вердикт. Докази по кожному кейсу — у `runs/<кейс>/`.
- **Код виходу:** 0, якщо всі кейси пройшли або пропущені; 1, якщо хоча б один упав. Зручно для CI.
- **Шляхи** з командного рядка рахуються від папки, з якої запущено команду; усе інше — від кореня проєкту. Тому скрипт працює з будь-якої папки, зокрема з IntelliJ (Run на `.mjs`-файлі запускає його з `scripts/`). Порядок аргументів довільний.
- **Потрібен** встановлений і залогінений Claude Code CLI (`claude`). Кейс коштує ~$0.1–0.3: більше, якщо знадобилась друга спроба.

## Як працює

```
тест-кейс (.md)            контекст проєкту                          перевірка
  кроки +          ──►  правила .claude/CLAUDE.md,        ──►  claude -p  ──►  tsc --noEmit  ──►  playwright test
  очікуваний            Page Objects / BookingApi,                (headless,          │                  │
  результат             фікстури, тестові дані,                    без tools)         └──── падіння ─────┘
                        приклад спеки                                                        │
                                                                    ◄── помилка + попередній код (--fix N)
```

1. **Вхід** — текстовий тест-кейс у `generator/cases/`. Перший рядок містить `Система: UI` або `Система: API`, далі передумова, кроки й очікуваний результат.
2. **Контекст.** Скрипт збирає промпт з правил `.claude/CLAUDE.md`, коду Page Objects (або `BookingApi`), фікстур, тестових даних і однієї наявної спеки як прикладу стилю. Модель бачить тільки цей контекст: `claude -p --tools ""` вимикає їй читання файлів і shell.
3. **Генерація.** Claude Code в headless-режимі (`claude -p --output-format json`) повертає одну спеку. Вона зберігається в `tests/<ui|api>/generated/<кейс>.spec.ts`, тобто потрапляє в загальний пул тестів і CI.
4. **Перевірка.** `tsc --noEmit`, потім `playwright test` тільки для цієї спеки.
5. **Виправлення.** Якщо typecheck або тест упали і задано `--fix N`, модель отримує помилку й свій попередній код. Промпт прямо забороняє послаблювати assertion, якщо застосунок поводиться не так, як описано в «Очікуваному результаті»: це може бути баг.
6. **Вердикт** у `summary.json`:
   - `passed`;
   - `possible product bug` — тест компілюється, а падає на assertion; потрібен тріаж людиною;
   - `failed at typecheck/test` — проблема в згенерованому коді.
7. **Докази.** Для кожного прогону в `generator/runs/<кейс>/` лежать промпт, сирі відповіді моделі, код кожної спроби, логи typecheck і тесту, `summary.json` (час, вартість, вердикт), а за потреби — diff ручних правок.

**Чого модель робити не може за правилами промпта:** вигадувати методи Page Objects. Якщо потрібного методу немає, вона пише локатор прямо в тесті і ставить над ним `// TODO(page-object): …`. Це і є список того, що треба доробити руками.

### 1. Вихід із системи

**Вхід:** [`cases/01-logout.md`](cases/01-logout.md). Відкрити меню → Logout → спробувати відкрити `/inventory.html` напряму. Очікувано: порожня форма логіну і помилка доступу.

**Згенерувалось:** [`runs/01-logout/attempt-1.spec.ts`](runs/01-logout/attempt-1.spec.ts). Модель:
- правильно знайшла `loggedIn`, `loginPage.username/password/error`, `loggedIn.goto()`;
- методу логауту в Page Objects не було, і вона **не вигадала** його, а вставила локатори прямо в тест з трьома `TODO(page-object)`;
- текст помилки винесла в константу з `TODO(data)`;
- `data-test="logout-sidebar-link"` вгадала правильно: модель не бачила сайт, але тест пройшов, отже атрибут справжній.

**Пройшов:** так, з першої спроби.

**Правили руками** ([diff спеки](runs/01-logout/manual-fix.diff); зміни в `src/` — у коміті разом з конвеєром):
- у `HeaderComponent` додали `openMenu()`, `logoutLink` і `logout()`, а `resetAppState()` тепер теж використовує `openMenu()`;
- у `ERRORS` додали `inventoryRequiresLogin`;
- у спеці замінили сирі локатори на методи Page Object. Логіка й assertion не змінились.

### 4. Кейс на відомий баг: чи не «підганяє» модель тест під баг?

**Вхід:** [`cases/04-empty-cart-checkout.md`](cases/04-empty-cart-checkout.md). Очікувано, що з порожнім кошиком користувач лишається на `/cart.html`. Насправді SauceDemo пускає на оформлення, це баг BUG-U1 з [`BUGS.md`](../BUGS.md).

**Що сталося:**
- **Спроба 1:** тест упав, `Expected pattern: /\/cart\.html$/`, `Received: ".../checkout-step-one.html"`.
- **Спроба 2:** модель отримала цю помилку з проханням виправити. Assertion вона **не послабила**, а залишила перевірку на `/cart.html`, зробила її м'якою і додала ще одну правильну перевірку: форма покупця не відкривається.
- **Вердикт:** `possible product bug`, бо тест компілюється і падає на assertion.

Кейс прогонявся двічі. Першого разу модель повернула на спробі 2 ідентичний код, другого — код з доданою перевіркою; [у `runs/`](runs/04-empty-cart-checkout/) лежить другий прогін. **Поведінка недетермінована**, тому вердикт визначається за типом падіння (assertion чи помилка коду), а не за тим, чи змінила модель код.

**Правили руками:** згенеровану спеку прибрали з `tests/`, бо вона дублює `UI-CHK-04`. Логи лишились у `runs/`.

## Обмеження й чесні примітки

- **Модель не бачить сайт.** Локатори, яких немає в Page Objects, вона вгадує. У прикладі 1 вгадала `logout-sidebar-link` правильно, але це не гарантовано. Неправильний локатор дасть timeout або strict mode violation, і вердикт буде `failed at test`, а не «баг».
- **Тест, що пройшов, ще не означає корисний тест.** Згенерований код переглядає людина, як і будь-який чужий PR. Тому в таблиці є колонка «що правили руками».
- **Недетермінованість.** Повторний запуск на тому самому кейсі може дати інший код (див. приклад 4).
- **Поле `verdict` додано в конвеєр після прогонів 1–3**, тож у їхніх `summary.json` його дописано вручну (`passed`, бо всі три пройшли). Для прогону 4 вердикт перераховано новою логікою з того самого збереженого логу, без повторного виклику моделі.
- **Вартість** — близько $0.11–0.15 за кейс. Повний контекст (`CLAUDE.md` + Page Objects + приклад спеки) — це основна частина промпта.
