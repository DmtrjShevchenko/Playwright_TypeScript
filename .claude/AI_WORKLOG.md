### Що зроблено

- **Перша версія (відхилена користувачем):** окремі спеки `known-bugs.spec.ts` з `test.fail()` і ручний `BUGS.md`.
- **Фінальна версія за вимогою користувача:** «баги мають бути в загальному пулі тестів, а баг-репорти — створюватися на підставі фейлів».
  - Тести на баги лежать у загальних спеках своєї області і перевіряють **правильну** поведінку, без `test.fail()`:
    - `checkout.spec.ts` — порожній кошик, поля з самих пробілів;
    - `cart.spec.ts` — Reset App State;
    - `booking.spec.ts` — 401 при невірному паролі, 404 для PUT/DELETE неіснуючого id, статус успішного DELETE, 5 перевірок валідації `POST /booking` (один параметризований тест).
  - **Репортер `src/reporters/bug-report.ts`** з кожного упалого тесту генерує баг-репорт:
    - кроки — з `test.step`, упалий крок позначено ❌;
    - очікуваний результат — з повідомлення assertion і рядка `Expected`;
    - фактичний результат — з рядка `Received`;
    - серйозність і передумова — з анотацій `severity` і `precondition`;
    - також оточення, повна помилка, скриншот і trace.
  - Звіт пишеться в `bug-reports/BUGS.md` (у git не потрапляє), у CI — в артефакт `bug-reports` і Summary job'а. Опублікована копія для README — `/BUGS.md`, оновлюється командою `npm run bugs:publish` (`scripts/publish-bugs.mjs`).
  - Змінено тести, які закріплювали поведінку API як є: `POST /auth` з невірним паролем тепер очікує 401 (було 200). CRUD-флоу при DELETE перевіряє тільки 2xx, а точний статус (200/204) перевіряє окремий тест.
  - Оновлено README (розділ «Знайдені баги»), `test-cases/` (23 кейси з колонкою статусу ✅/❌) і правила в `.claude/CLAUDE.md` (розділ «Баги»).
  - Дві знахідки не автоматизовані, бо потребують уточнення вимог: довільні символи в полях чекауту і скидання сортування після повернення зі сторінки товару.

### Рішення та чому
- **Червоний тест = відкритий баг.** CI буде червоним, поки баги не виправлені, — це свідомий наслідок вимоги «репорти з фейлів». `test.fail()` ховав би баги за зеленим CI.
- **Тест, що пройшов на retry (flaky), багом не вважається**: у репорт потрапляє тільки фінальний результат.
- **Флоу не падає через другорядну розбіжність** (код статусу DELETE), бо інакше він ховав би перевірки, що йдуть після неї.
- **Кілька незалежних перевірок в одному тесті — через `expect.soft`**, щоб репорт показав усі розбіжності, а не тільки першу.

### Де агент помилився і як це помітили
- **Окремі спеки для багів з `test.fail()`.** Користувач відхилив підхід: баги мають бути в загальному пулі тестів, а репорти — з падінь.
- **Локатор у скрипті дослідження.** `getByRole('button')` усередині картки товару знайшов ще й два посилання, і скрипт упав на strict mode. Агент помітив це з помилки та виправив на `locator('button')`.
- **Перевернутий assertion.** `expect([200, 204]).toContain(status)` у репорті показав фактичне значення як `[200, 204]` замість статусу. Агент помітив це в згенерованій таблиці багів і переписав на `expect(String(status)).toMatch(/^(200|204)$/)`.
- **`--list` затирав звіт.** `npx playwright test --list` теж викликав репортер і перезаписав `bug-reports/BUGS.md` порожнім звітом. Агент помітив це за лічильником репортів після `--list` і додав перевірку «жоден тест не запускався — звіт не чіпати».
- **`awk` мовчки видалив розділ README.** Шлях до тимчасового файлу у форматі Windows не прочитався, і старий розділ видалився без вставки нового. Агент помітив це, перевіривши заголовки README після правки, і вставив розділ через Edit.
- **`;` у npm-скрипті.** На Windows npm виконує скрипти через `cmd`, де `;` не розділяє команди. Агент помітив це до запуску і виніс публікацію в `scripts/publish-bugs.mjs`.

### Перевірка
- `npm run typecheck` — без помилок.
- `npm run bugs:publish`: 23 тести, **12 passed, 11 failed**, згенеровано 11 баг-репортів, `BUGS.md` опубліковано.
- `npx playwright test --list` після фіксу не змінює звіт.
- Зміни не закомічені; CI з новими тестами ще не запускався.

### Відкрито
- Скриншоти й trace у `/BUGS.md` вказують на локальну папку `test-results/`, якої немає в репозиторії; у CI вони лежать в артефакті `test-results`.
- Нумерація `BUG-NN` у згенерованому звіті залежить від набору падінь і може змінюватися між прогонами.
