# API тест-кейси — Restful Booker

**Система:** https://restful-booker.herokuapp.com ([документація](https://restful-booker.herokuapp.com/apidoc))
**Заголовки всіх запитів:** `Accept: application/json`, `Content-Type: application/json`
**Облікові дані:** `admin` / `password123`
**Авторизація для PUT/DELETE:** заголовок `Cookie: token=<token>`

**Тестове бронювання** (генерується для кожного тесту, прізвище унікальне):

```json
{
  "firstname": "Autotest",
  "lastname": "PW-<8 випадкових символів>",
  "totalprice": 150,
  "depositpaid": true,
  "bookingdates": { "checkin": "2027-01-10", "checkout": "2027-01-15" },
  "additionalneeds": "Breakfast"
}
```

---

## API-BOOK-01 · CRUD-флоу бронювання
- **Тип / Пріоритет:** Позитивний / P1
- **Передумова:** немає. Тест сам створює і видаляє свої дані.

| # | Запит | Очікуваний результат |
|---|---|---|
| 1 | `POST /auth` з `admin` / `password123` | **200**, у тілі є `token` (рядок) |
| 2 | `POST /booking` з тестовим бронюванням | **200**, у тілі `bookingid` (число) і `booking`, що дорівнює надісланим даним |
| 3 | `GET /booking/{id}` | **200**, тіло дорівнює створеному бронюванню |
| 4 | `PUT /booking/{id}` з токеном і зміненими даними: `firstname: "Updated"`, `totalprice: 999`, `depositpaid: false`, дати `2027-02-01`–`2027-02-03`, `additionalneeds: "Late checkout"` | **200**, тіло дорівнює зміненим даним |
| 5 | `GET /booking/{id}` | **200**, тіло дорівнює зміненим даним |
| 6 | `DELETE /booking/{id}` з токеном | **201** Created — задокументована відповідь API (за семантикою HTTP очікувався б 200/204, тому в README це винесено в розділ «Задокументовано, але розходиться з HTTP-семантикою», а не в баги) |
| 7 | `GET /booking/{id}` | **404**: бронювання більше немає |

## API-AUTH-01 · Авторизація з невірним паролем
- **Тип / Пріоритет:** Негативний / P1
- **Статус:** ❌ падає — баг (повертає **200** з `{"reason":"Bad credentials"}`)

| # | Запит | Очікуваний результат |
|---|---|---|
| 1 | `POST /auth` з `admin` / `wrong-password` | **401** Unauthorized, поля `token` у відповіді немає |

## API-BOOK-02 · Оновлення бронювання без токена
- **Тип / Пріоритет:** Негативний / P1
- **Передумова:** створено тестове бронювання (`POST /booking`).

| # | Запит | Очікуваний результат |
|---|---|---|
| 1 | `PUT /booking/{id}` **без** заголовка `Cookie`, з `firstname: "Hacker"` | **403** Forbidden |
| 2 | `GET /booking/{id}` | Бронювання не змінилось: тіло дорівнює початковим даним |

- **Прибирання:** бронювання видаляється (`DELETE` з токеном), навіть якщо тест упав.

## API-BOOK-03 · Отримання неіснуючого бронювання
- **Тип / Пріоритет:** Негативний / P3

| # | Запит | Очікуваний результат |
|---|---|---|
| 1 | `GET /booking/2147000000` | **404** Not Found |

> Сервер публічний і спільний для всіх. Id `2147000000` обрано настільки великим, щоб не збігтися з реальним бронюванням.

## API-BOOK-05 · Зміна й видалення неіснуючого бронювання
- **Тип / Пріоритет:** Негативний / P3
- **Статус:** ❌ падає — баг (обидва запити повертають **405** Method Not Allowed)

| # | Запит | Очікуваний результат |
|---|---|---|
| 1 | `PUT /booking/2147000000` з валідним тілом і токеном | **404** Not Found: метод підтримується, відсутній саме ресурс |
| 2 | `DELETE /booking/2147000000` з токеном | **404** Not Found: метод підтримується, відсутній саме ресурс |

> Обидві перевірки «м'які» (`expect.soft`): тест перевіряє обидва запити, навіть якщо перший уже впав.

## Валідація `POST /booking`

Один параметризований автотест для п'яти невалідних тіл. Для кожного очікується **400 Bad Request** і те, що бронювання не створене.
Якщо API помилково створює бронювання, тест одразу його видаляє, щоб не залишати сміття на спільному сервері.

| ID | Пріоритет | Тіло запиту (відносно тестового бронювання) | Очікуваний результат | Статус |
|---|---|---|---|---|
| API-VAL-01 | P2 | без поля `firstname` | **400** | ❌ повертає **500** |
| API-VAL-02 | P1 | `"totalprice": "abc"` | **400** | ❌ **200**, ціна зберігається як `null` |
| API-VAL-03 | P2 | невалідний `"checkin": "2027-13-45"`, `checkout` валідний (`"2027-01-10"`) | **400** | ❌ **200**, `checkin` зберігається як `"0NaN-aN-aN"` |
| API-VAL-04 | P2 | `"checkin": "2027-01-15"`, `"checkout": "2027-01-10"` | **400** | ❌ **200**, бронювання створено |
| API-VAL-05 | P1 | `"totalprice": -100` | **400** | ❌ **200**, збережено −100 |
